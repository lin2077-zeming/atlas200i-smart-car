# 项目总览导读（Atlas 200I DK A2 人机交互小车）

> 本文是《../3.硬件与供电/硬件组装.md》的昇腾改版：项目背景与总体设计沿用原方案，计算底座由「瑞芯微 RK3576 + 银河麒麟」迁移到「昇腾 310B + Ubuntu 22.04」，并依据新平台的真实能力边界重新划分算力负载、选择构筑路线。
>
> 文中所有硬件规格、接口、默认账号、软件版本均对齐昇腾社区官方文档；标注「预计」的数值为工程估算，需在实机上校准。

---

## 一、项目背景

### 1.1 原方案要解决的问题（不变）

随着大语言模型技术的快速发展，"让机器听懂人话、回应人话、执行任务"的三位一体交互模式已成为人机交互领域的前沿方向。当前主流方案普遍存在两个痛点：

1. **过度依赖云端算力。** 市面智能音箱/助手将语音数据上传云端处理，存在网络延迟高（300–800 ms）、隐私泄露风险大、断网即失效等问题。
2. **缺少物理世界执行能力。** 现有对话系统大多停留在"聊天"层面，无法将语音指令转化为对真实设备的控制动作。

项目的核心命题——**全国产化软硬件平台上的离线边缘智能交互系统**——保持不变。

### 1.2 平台迁移带来的新问题

原方案以 RK3576（内置 6 TOPS NPU）+ 银河麒麟为核心底座，端侧跑通 ASR → LLM → TTS 全管线。更换为 Atlas 200I DK A2 后，**不能简单地把旧方案原样搬过去**，因为两个平台的强弱项几乎是互补的：

| 维度 | RK3576（原） | Atlas 200I DK A2（新） | 影响 |
|---|---|---|---|
| AI 算力 | 6 TOPS INT8，单核实际约 2 TOPS | **8 TOPS INT8 / 4 TFLOPS FP16**，达芬奇架构，算力可稳定打满 | 净提升，值得把重负载往 NPU 挪 |
| CPU 算力 | 4×A72@2.2G + 4×A53@1.8G（8 核） | **4×TaiShanV200M@1.0GHz（4 核）** | **显著下降**，原方案里跑在 CPU 上的 ASR/TTS 会吃紧 |
| 内存 | 通常 4–8 GB | **4 GB LPDDR4X（ECC），带宽 25.6 GB/s** | 可跑小模型，7B 以上无望 |
| 视频编解码 | 有 NPU，缺硬件编解码通路 | **DVPP 硬解 20 路 1080P@30fps + 硬件编码** | **新增能力**，视觉模态从"能跑"变成"好用" |
| AI 工具链 | RKNN（半封闭，社区支持弱） | **CANN + MindStudio + ATC + AscendCL + MindX SDK**（官方全栈、文档齐全） | 工程确定性大幅提升 |
| 生态样例 | 需自行拼装 | **官方 E2E 样例：智能小车 / 机械臂 / 智能语音台灯 / Chatbot / 机械狗** | 有官方参考实现可直接对齐，不必从零 |
| 无线连接 | 板载 WiFi | **无板载 WiFi**，需 M.2 Key E 模块或 USB 网卡 | 需补配件 |
| 供电 | 5V/3A 级 | **12V，典型 24W（实测 8–15W）** | 车载电源方案需重做 |

**一句话结论**：新平台**AI 更强、CPU 更弱、外设更工业、工具链更规范**。因此构筑路线的核心不是"照搬"，而是**把原来压在 CPU 上的推理负载尽量搬到 NPU，把 CPU 腾出来只做控制与调度**。

## 二、设备条件分析

### 2.1 硬件规格（Atlas 200I DK A2 标准版）

| 项目 | 规格 | 对本项目的意义 |
|---|---|---|
| AI 处理器 | 昇腾 310B4（1×DaVinciV300 AI Core，500 MHz） | `npu-smi info` 中 `Chip Name = 310B4` |
| AI 算力 | 8 TOPS INT8 / 4 TFLOPS FP16（默认档位 `8T_1.0GHz`） | 足够跑 ASR / TTS / YOLO 级别的模型 |
| CPU | 4×TaiShanV200M（ARMv8，**1.0 GHz**） | **项目的第一瓶颈**，只够做控制/调度/轻量推理 |
| 内存 | LPDDR4X 4 GB，支持 ECC，带宽 25.6 GB/s | 决定 LLM 上限约 0.5B–1.5B（量化后） |
| 存储 | MicroSD（系统盘）+ M.2 Key M（可加 NVMe SSD） | **强烈建议加装 NVMe**：系统盘用 SD 卡会拖慢模型加载 |
| 视频编解码 | 20 路 1080P@30fps 硬解 / 2 路 4K@75fps；12 路 1080P 硬编 | 视觉模态的硬件基础（DVPP） |
| 典型功耗 | 24 W（官方标称），原装 12V/2A 适配器 | 车载供电设计依据 |
| 算力档位 | 8T 版可切 `8T_1.0GHz` / `4T_1.0GHz` | 电池续航紧张时可降档换功耗 |

> **关于 8T / 20T 版本**：昇腾官方定义 `310B4 = 8T 算力规格`、`310B1 = 20T 算力规格`，而 **Atlas 200I DK A2 开发者套件默认算力档位为 `8T_1.0GHz`（4 GB 内存版）**。若手上是 20T/12G 定购型号，`atc` 转换时 `--soc_version` 必须相应改为 `Ascend310B1`（见 §5.4.4）。**每次开发前先确认**：
> ```bash
> npu-smi info -t board -i 0 -c 0 | grep "Chip Name"   # 310B4 = 8T；310B1 = 20T
> ```

### 2.2 接口清单与"可用口预算"

这是本项目最容易翻车的地方——**板子外设虽多，但能用的 USB 口只有 2 个 Type-A + 1 个 Type-C**，而我们需要同时接：串口转接、麦克风、扬声器、摄像头、WiFi。

| 接口 | 数量 | 计划用途 | 备注 |
|---|---|---|---|
| USB 3.0 Type-A | 2 | ① **USB 声卡（麦克风+音箱二合一）** ② 预留/摄像头 | 若用板载 Type-C 接小车（串口3=`ROS` 口）可省掉 USB-TTL 模块，USB-A 就空出来了 |
| USB 3.0 Type-C | 1 | 调试/制卡虚拟网口（192.168.0.2） | 不建议占用 |
| RJ45 千兆网口 | 2（eth0 / eth1） | eth0 接车内路由器；eth1 直连笔记本（默认静态 `192.168.137.100`） | 有线优先，最稳 |
| MIPI-CSI 51pin | 2 | **广角摄像头模组（走 MIPI，不占 USB）** | 关键：把摄像头从 USB 挪到 CSI，省出 USB 口 |
| MIPI-DSI 51pin | 1 | 预留（可接小屏） | — |
| HDMI | 2 | **仅 HDMI0 可用**（HDMI1 为预留，当前不可用） | 接显示器做本地 GUI |
| 40-pin 扩展口 | 1 | 预留（I2C/SPI/UART 扩展传感器） | 谨慎复用，避免与 MIPI 冲突 |
| M.2 Key M | 1 | NVMe SSD（2242/2280） | 建议加装 |
| M.2 Key E | 1 | **WiFi/蓝牙模块** | 板载无 WiFi，必配 |
| MicroSD | 1 | 系统镜像盘 | 建议 U3/A2 级别，≥32 GB |

> **结论：必须加一个「带外部供电的 USB 3.0 Hub」**，用于摄像头调试、激光雷达、U 盘等临时外设；但**长期驻留的关键外设（串口、声卡）要直接插板载口**，不要经过 Hub，避免枚举抖动导致串口掉线。

**音频要点（务必注意）**：Atlas 200I DK A2 **只有 1 个板载 MIC，没有 3.5 mm 音频输出口**。因此 TTS 的播放必须走 **USB 声卡 / USB 音箱**（或 HDMI 音频）。原方案用的 USB 麦克风可以继续用，但更推荐 **USB 声卡（麦克风输入 + 扬声器输出一体）**，一次占一个口、解决录音与放音两件事。

## 三、构筑路线选型（核心决策）

### 3.1 选型准则

1. **CPU 是最稀缺资源**——凡是可以放 NPU 的推理，都不要留在 CPU。
2. **关键路径必须离线且确定**——急停、手动控制不经过任何大模型，延迟与可靠性可预测。
3. **优先复用已验证资产**——上一代项目打磨过的串口协议、运动控制层、KWS 急停、远程调试链路，能复用的绝不重写。
4. **一期不碰高风险项**——CANN 升级、LLM 上 NPU、自研算子等留到二期。

### 3.2 决策一：底盘与下位机

| 方案 | 说明 | 优点 | 缺点 | 判断 |
|---|---|---|---|---|
| **甲：沿用 STM32F407 底盘** | 保留 4 路编码电机 + PID 速度闭环 + MPU6050 + 11/24 字节自研协议 | `car_serial.py` / `motion_control.py` **可 100% 复用**；速度闭环带来可控的运动精度；安全机制（低压保护、急停标志、物理使能开关）已成型 | 需确认底盘仍在且下位机固件未丢 | ✅ **推荐** |
| 乙：改用官方 ESP32 小车方案 | 照抄官方 TT 电机 + 麦轮 + ESP32 | 与官方样例完全对齐，有 3D 结构件与样例代码 | 需重做下位机；TT 电机**无编码器**，无速度闭环，运动精度差；官方语音模式未实现 | ❌ 仅作结构件/外观参考 |

**选甲。** 迁移到 Atlas 只需要改一个字符串：串口设备名。同时把官方小车的**外壳/结构件设计**作为可选的机械升级参考（官方提供 3D 结构件）。

> **串口设备名提示**：下位机板载的 USB 转串口芯片是 **CH9102**（不是 CH343，据厂商《STM32F407VET6 主板资源分配 V2.4》："PA9/PA10 → 串口1 → CH9102F"、"PD8/PD9 → 串口3 → CH9102F"）。CH9102 与 CH340/CH343 共用 Linux 的 `ch341` 内核驱动，**在 Linux 上同样枚举为 `/dev/ttyUSB0`**（`ch341-uart` 驱动），而非原代码默认的 `/dev/ttyACM0`。建议用 udev 规则固定一个别名，避免插拔顺序变化导致设备名漂移：
> ```bash
> # /etc/udev/rules.d/99-car.rules
> SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="55d3", SYMLINK+="ttyCAR"
> ```
> 之后代码统一用 `CarSerial("/dev/ttyCAR")`。
>
> 💡 **可以省掉 USB-TTL 模块**：下位机主板丝印有 `ROS` 标记的 Type-C 口就是串口3（ROS 通信口）。
> 直接用 Type-C 数据线连到 Atlas 的 Type-C 口即可 —— **省下一个宝贵的 USB-A 口**（Atlas 只有 2 个 USB-A）。


### 3.3 决策二：认知决策层（LLM）放在哪里 —— 最关键的决策

这是整个方案里风险最高、也最需要想清楚的一步。

| 方案 | 做法 | 可行性 | 性能（预计） | 风险 |
|---|---|---|---|---|
| **A. NPU 跑 LLM（ATC→OM）** | 把 Qwen2.5-0.5B/1.5B 转成 `.om` 用 AscendCL 推理 | ⚠️ 低 | 若成功最快 | LLM 是动态 shape + KV Cache + RoPE，ATC 图转换需大量改造甚至自定义算子；MindIE 官方未把 200I DK 列入支持清单；4 GB 内存容纳 1.5B 权重 + KV 极紧张 |
| **B. CPU 跑 LLM（llama.cpp / Ollama）** | Qwen2.5-0.5B-Instruct **Q4_K_M**（约 400 MB） | ✅ 高 | 单次输出约 15–25 token，**响应 2–5 s**（预计） | 4 核 @1.0 GHz，长文本慢；但**我们的输出极短**，可接受 |
| **C. 纯云 API** | 走在线大模型 | ✅ 高 | 最快最好 | **断网即失效，直接推翻项目核心卖点** | 
| **D. NPU 跑专用小模型替代 LLM** | 意图分类 + 槽位抽取（TextCNN / BERT-tiny）转 `.om` | ✅ 中高 | < 50 ms | 泛化能力弱于 LLM，但**小车指令空间本就封闭**，足够用 |

**推荐路线：B 为主 + D 为快路径 + C 为可选增强，A 列入二期探索。**

具体做法：

- **主路径（B）**：CPU 上跑 `Qwen2.5-0.5B-Instruct`（Q4_K_M GGUF），用 **llama.cpp 的 GBNF 语法约束解码**，强制输出严格 JSON。这一步是性能关键——把"自由生成"变成"受限填槽"，输出长度从数十 token 压到 ~15 token，延迟直接砍半。
  - 若确认是 12 GB 版可升级到 `Qwen2.5-1.5B-Instruct`，效果更好、延迟约翻倍。
- **快路径（D）**：对高频指令（前进/后退/左转/右转/停止/急停/速度调节）先过一遍**规则 + 关键词**匹配，命中直接执行，**不走 LLM**。这覆盖了实际使用中 80% 以上的指令，把 LLM 留给"前进一米""慢慢往后倒一点""绕过这个障碍"这类需要语义消歧的表达。
- **增强路径（C）**：保留一个可开关的云 API 后端，在演示环境有网时提供更自然的对话体验；**默认关闭**，断网自动降级到 B。

**为什么不让 LLM 上 NPU**：把 NPU 留给 ASR、TTS、视觉三件事，收益远大于死磕 LLM 的图转换。NPU 的确定性收益 vs LLM-on-NPU 的不确定性风险，选择前者。

### 3.4 决策三：ASR / TTS 放在哪里

| 模块 | 路线 | 说明 |
|---|---|---|
| **ASR 主识别** | 一期 CPU，二期 **NPU** | sherpa-onnx + SenseVoice-Small。CPU 上实时率预计 0.4–0.6（< 1 即实时），够用；但会吃掉 2 个核，**二期移到 NPU 后 CPU 才能腾给 LLM 和调度** |
| **KWS 语音急停** | **CPU（必须独立）** | 直接复用已验证的 sherpa-onnx Zipformer KWS 方案（详见《../6.历史资料/上一代RK3576-KWS方案.md》）。**急停必须与 ASR/LLM 线程隔离**，任何情况下不能被主流程阻塞 |
| **TTS** | 一期 CPU + **预合成缓存**，二期 NPU | VITS 类模型在 1.0 GHz A55 上实时率可能 > 1（慢于实时）。对策：① 换用更轻的 **Matcha-TTS**（非自回归，比 VITS 快数倍）；② 对高频短回复（"好的""正在前进""已停止"）**离线预合成后缓存 WAV**，运行时直接播放，平均延迟几乎为零 |

> **关于 sherpa-onnx 上昇腾 NPU**：sherpa-onnx 已支持 Ascend NPU（源码编译加 `-DSHERPA_ONNX_ENABLE_ASCEND_NPU=ON`，运行时 `provider="ascend"`），但**要求 CANN 8.x**，且官方预导出的 `.om` 目前是 **310P3** 的，**310B4 需要自行用 ATC 导出**。因此这是二期任务，且需要先评估 CANN 升级对官方镜像的影响。

### 3.5 决策四：人机交互模态

原方案是纯语音。Atlas 的 NPU + DVPP 硬解让**视觉模态变得便宜**，而"人机交互"本身就应该多模态。

| 模态 | 实现 | 放哪 | 优先级 |
|---|---|---|---|
| 语音（听 + 说） | ASR + LLM + TTS | CPU（一期）/ NPU（二期） | P0 |
| **视觉（看）** | MIPI-CSI 广角摄像头 → DVPP 硬解 + 缩放 → **YOLOv5/YOLOv8 `.om`** → 手势/人体/障碍物 | **NPU** | **P1（本次核心增量）** |
| 手动控制 | 键盘（`termios` 非阻塞）或 GUI 方向键 | CPU | P0 |
| 距离感知 | 沿用超声波（接 STM32）或新增 | STM32 | P2 |

视觉模态最有价值的三个应用：**① 手势控车**（"挥手即停"是比语音更快的急停手段）；**② 人体跟随**；**③ 前方障碍物预警**（与超声波互补）。

### 3.6 决策五：应用展示层（GUI 框架）

原项目在银河麒麟上尝试 PySide6 失败（ARM 麒麟无官方预编译包），最终退到 Tkinter。**这个结论在 Atlas + Ubuntu 22.04 上不成立**：

- PySide6 自 6.6 起提供 **`manylinux_2_28_aarch64` 预编译 wheel**，Ubuntu 22.04（glibc 2.35）可直接 `pip install PySide6`。
- 系统 Python 3.9.2 在 PySide6 6.7.x 的支持区间内（wheel 为 `cp39-abi3`，兼容 3.9+）。

| 方案 | 可行性 | 说明 |
|---|---|---|
| **PySide6 + QML / Widgets** | ✅ **推荐** | 复用原项目的 UI 设计资产；流式气泡、状态监控都成熟 |
| Tkinter | ✅ 保底 | 零依赖、必定能跑，样式朴素 |
| Web（FastAPI + 浏览器） | ✅ 推荐作**第二界面** | 官方 Chatbot 样例就是 Web 形态；便于远程用笔记本浏览器控制，适合演示 |

**建议：主界面 PySide6 跑在 HDMI0 本地屏；同时提供一个 Web 控制台，用于远程演示和调试。** 若 PySide6 安装遇到问题，立即降级 Tkinter，不在此处消耗工期。

### 3.7 最终推荐路线一览

| 层 | 组件 | 部署位置 | 来源 |
|---|---|---|---|
| 交互感知 | KWS 语音急停（Zipformer） | CPU（独立线程） | **复用**上一代方案 |

### 4.2 资源分配预算（4 核 CPU 是硬约束，必须提前分配）

| CPU Core 0–1 | ASR / TTS / 视觉后处理 | 推理线程 |

**供电设计（比原方案更吃紧，必须重新算）**

### 5.4 交互感知层

#### 5.4.1 KWS 语音急停（P0，直接复用）

完全沿用《../6.历史资料/上一代RK3576-KWS方案.md》的方案，只改三处：

| 项 | 原（RK3576 / 麒麟） | 新（Atlas / Ubuntu） |
|---|---|---|
| 模型路径 | `/home/kylin/modelplayer/kws/...` | `/home/HwHiAiUser/models/kws/...`（或 `/data/models/`） |
| 麦克风设备号 | USB 麦克风 device 1 @44100 | 换成 **USB 声卡**，用 `arecord -l` 重新确认设备号 |
| 运行方式 | `python emergency_kws_monitor.py` | 建议做成 `systemd` 服务，**开机自启**，权限单独配置 |

**纪律不变**：① 急停程序不导入小车控制代码；② 不做单字"停"作为一级急停词；③ 语音急停**不能替代物理急停按钮**和底盘看门狗；④ 必须实测误触发率（电机噪声、胎噪、音乐、他人说话等场景）。

#### 5.4.2 ASR 主识别

一期直接用 sherpa-onnx + SenseVoice-Small（`sherpa-onnx-sense-voice-zh-en-ja-ko-yue-2024-07-17`）：

```bash
python3 -m pip install sherpa-onnx sounddevice numpy
arecord -l                     # 确认 USB 声卡设备号
python3 -c "import sounddevice as sd; print(sd.query_devices())"
```

- **采样率适配**：沿用软件的"设备采样率 → 16 kHz"重采样层（sherpa-onnx 内部支持重采样，不用像原方案那样手写 3:1 降采样）。
- **实时率目标**：RTF < 0.5。若实测 > 0.8，先把 `num_threads` 提到 3、关闭其他推理任务再测。
- **二期上 NPU**：见 §5.4.4。

#### 5.4.3 TTS 语音合成

| 策略 | 做法 |
|---|---|
| **① 预合成缓存（必做）** | 把系统所有固定回复（"好的，正在前进""已停止""电量偏低，请充电""没有听懂，请再说一遍"等约 30 条）离线合成为 WAV 缓存，运行时直接播放。**平均 TTS 延迟趋近于 0** |
| ② 换轻模型 | 用 **Matcha-TTS**（非自回归）替代 VITS，速度快数倍 |
| ③ 流式播放 | 长文本按句切分、边合成边播 |
| ④ 二期上 NPU | 同 §5.4.4 |

#### 5.4.4 二期：把 ASR/TTS 搬到 NPU

**目标**：CPU 只保留控制与调度，为 LLM 让出 2 个核。

**路线：ATC 将 ONNX 转成 `.om`**（参考 sherpa-onnx 官方的昇腾导出流程）

```bash
source /usr/local/Ascend/ascend-toolkit/set_env.sh
# soc_version 必须与实测芯片一致：
#   310B4 (8T)  → --soc_version=Ascend310B4     ← 开发者套件标准版
#   310B1 (20T) → --soc_version=Ascend310B1
atc --model=./model.onnx \
    --framework=5 \
    --host_env_os=linux \
    --host_env_cpu=aarch64 \
    --output=model \
    --input_format=ND \
    --input_shape="x:1,-1,560;prompt:4" \
    --soc_version=Ascend310B4
```

**前置条件与风险**：
1. sherpa-onnx 的 Ascend 支持**要求 CANN 8.x**，而官方镜像是 CANN 7.0.RC1 → **需先评估 CANN + 驱动同步升级的可行性**（建议在备份镜像上先试）。
2. sherpa-onnx 需要用**源码编译**（`-DSHERPA_ONNX_ENABLE_ASCEND_NPU=ON`），且在 x86 开发机上交叉准备离线依赖。
3. 官方只有 **310P3** 的预置 `.om`，`310B4` 必须自行导出并实测精度。
4. **若二期受阻，一期方案（CPU 版）继续可用**，不影响项目交付——这是刻意保留的降级路径。

#### 5.4.5 视觉感知（本次核心增量，P1）

```
MIPI-CSI 广角摄像头
      ↓
DVPP 硬件解码 + 缩放（不占 CPU）
      ↓
YOLOv8/YOLOv5 .om（NPU 推理，8 TOPS）
      ↓
后处理（CPU，轻量）→ 交互事件
      ↓
手势识别 / 人体跟随 / 障碍物预警
```

**模型转换**（以 YOLOv5s 为例，官方文档中的标准命令）：

```bash
atc --model=yolov5s.onnx --framework=5 \
    --output=yolov5s_bs1 --input_format=NCHW \
    --soc_version=Ascend310B4 \
    --input_fp16_nodes="images"
```

**落地的三个功能（按优先级）**：
1. **"挥手即停"**：识别到特定手势 → 直接触发与 KWS 同级的急停事件。**这比语音快，且不受噪声影响**，是很好的安全冗余。
2. **人体跟随**：目标框中心偏离画面中线 → 生成 Z 轴角速度指令，与原有 `set_speed(x, y, z)` 接口天然吻合。
3. **障碍物预警**：YOLO 检测到近距目标 + 超声波测距 → 分级限速。

**参考**：官方样例仓 `ascend-devkit/src/E2E-Sample/Car` 已实现"自动行驶/自动泊车/目标跟踪"，可直接借鉴其摄像头取流与推理管线；`ascend_community_projects`（`310B` 分支）有更多模型适配脚本。

### 5.5 认知决策层

#### 5.5.1 三层决策路由

```
用户文本
   │
   ├─ ① 规则/关键词快路径 ── 命中 ──→ 直接生成动作 JSON（< 10 ms）
   │      （前进/后退/左转/右转/停止/急停/加速/减速 ...）
   │
   ├─ ② LLM 受限解码路径 ────→ Qwen2.5-0.5B + GBNF → 严格 JSON（2–5 s）
   │      （"前进一米""慢慢往后倒一点""原地转个圈""绕过它"）
   │
   └─ ③ 兜底对话路径 ────────→ 口语化回复（≤ 50 字）→ TTS，不下发运动指令
```

#### 5.5.2 GBNF 语法约束（关键工程技巧）

llama.cpp 支持用 GBNF 语法强制输出结构，把"自由生成"变成"受限填槽"，**输出长度从数十 token 压到 ~15 token**，这是 CPU 场景下的性能救命稻草：

```gbnf
root        ::= control | chat
control     ::= "{" ws "\"type\"" ws ":" ws "\"control\"" ws "," ws
                "\"action\"" ws ":" ws action ws "," ws
                "\"speed\"" ws ":" ws number ws "," ws
                "\"duration\"" ws ":" ws number ws "}"
chat        ::= "{" ws "\"type\"" ws ":" ws "\"chat\"" ws "," ws
                "\"reply\"" ws ":" ws string ws "}"
action      ::= "\"forward\"" | "\"backward\"" | "\"turn_left\"" | "\"turn_right\""
              | "\"strafe_left\"" | "\"strafe_right\"" | "\"stop\""
number      ::= "-"? [0-9]+ ("." [0-9]+)?
string      ::= "\"" ([^"\\] | "\\" .)* "\""
ws          ::= [ \t\n]*
```

#### 5.5.3 System Prompt 设计要点

沿用原项目的意图分类思路，但**加上安全约束与物理量换算规则**：

```
你是智能小车的指令解析器。仅输出 JSON，不要输出任何解释。

可用动作与物理含义：
- forward / backward：X 轴线速度，单位 mm/s，建议区间 50–400
- turn_left / turn_right：Z 轴角速度（**注意：协议单位是 0.001 rad/s，不是 mm/s**），建议区间 50–300
- strafe_left / strafe_right：Y 轴（麦轮平移），建议区间 50–300
- stop：立即停止

换算规则（务必使用）：
- "前进一米" ≈ 前进 300 mm/s 持续 3.3 秒
- "左转 90 度" ≈ turn_left Z 值 ≈ 1570（即 1.57 rad/s）持续 1 秒
  ← 依据：Z 轴物理量是角速度，Z值 × 0.001 = rad/s；90° = 1.5708 rad
  ⚠️ 此值未实机标定，首次使用前必须用"左转90度"实测修正

安全规则（最高优先级）：
- 无法确定意图、涉及危险动作、或与运动无关的内容，一律返回 chat 类型
- speed 绝对值不得超过 400；duration 不得超过 5.0
- 任何"停下""别动""急停"类语义必须返回 stop，且 speed=0, duration=0
```

#### 5.5.4 意图→动作映射表（沿用并扩展）

| 自然语言 | action | speed | 说明 |
|---|---|---|---|
| 前进 / 往前走 | forward | 300 | X 轴正方向 |
| 后退 / 往后倒 | backward | 200 | X 轴负方向 |
| 左转 / 往左拐 | turn_left | 200 | Z 轴负角速度 |
| 右转 / 往右拐 | turn_right | 200 | Z 轴正角速度 |
| 左/右平移 | strafe_left / strafe_right | 200 | Y 轴（仅麦轮） |

#### 5.5.5 与旧代码对接

决策层输出与原有的 `MotionController` 无缝衔接（**零改动**）：

```python
# 决策层 -> 执行层
ACTION_MAP = {
    "forward":      lambda s, d: mc.forward(speed=s, duration=d),
    "backward":     lambda s, d: mc.backward(speed=s, duration=d),
    "turn_left":    lambda s, d: mc.turn_left(speed=s, duration=d),
    "turn_right":   lambda s, d: mc.turn_right(speed=s, duration=d),
    "strafe_left":  lambda s, d: mc.strafe_left(speed=s, duration=d),
    "strafe_right": lambda s, d: mc.strafe_right(speed=s, duration=d),
    "stop":         lambda s, d: mc.stop(),
}
# speed/duration 强制钳位，防止 LLM 幻觉给出危险值
speed    = max(-400, min(400, speed))
duration = None if duration <= 0 else min(5.0, duration)
ACTION_MAP[action](speed, duration)
```

| # | 风险 | 影响 | 应对 |

| R1 | 4 核 @1.0 GHz CPU 不足以同时跑 ASR + LLM + GUI | 交互延迟高，体验差 | ① 规则快路径覆盖高频指令；② 预合成 TTS 缓存；③ 二期 ASR/TTS 上 NPU；④ 严格线程绑核 |

| R9 | 被动散热 + 封闭外壳热降频 | 长时间推理性能骤降 | 加装风扇接风扇接口；监控 `npu-smi info` 温度 |

### E. 下位机（小车底盘）已核实规格

> 依据：`../3.硬件与供电/厂商资料/` 目录下的厂商资料 + 固件源码 `robot_select_init.h` / `usartx.h` / `balance.c`。
> 完整核对报告见《../3.硬件与供电/器件核对报告.md》。

| 项 | 值 | 对我们的影响 |
|---|---|---|
| 主控 | **STM32F407VET6** + FreeRTOS | ✅ 与假设一致 |
| 车型 | **M500 麦克纳姆轮四驱车**（`M500_MEC=1`，125 mm 麦轮） | ✅ Y 轴平移可用 |
| 电机 | 4× 直流电机，减速比 **50:1** | 速度上限受机械约束 |
| 编码器 | **13 线霍尔 ×4 倍频** = 52 counts/圈（电机轴） | 闭环精度有限，位置控制误差偏大 |
| 轮距/轴距 | 半轮距 0.173 m / 半轴距 0.149 m | 麦轮按半值定义 |
| 驱动器 | 大功率驱动器 V3，板载 **AT8236**，最大 2 A | 单轮峰值电流有限 |
| 传感器 | 板载 **MPU6050** 六轴 | ✅ 上行帧已含姿态，无需额外 IMU |
| 通信 | 串口1 + **串口3（Type-C，`ROS` 口）** + CAN(1Mbps) + 蓝牙 + PS2/航模 | 串口3 是官方 ROS 通信口 |
| **控制模式优先级** | **串口3（ROS）最高** —— 只要有数据就强制进入 ROS 模式 | ✅ 不用做模式切换；⚠️ 但会抢走遥控器控制权 |
| **开机保护** | 上电后 **10 秒**内电机强制失能、串口不收数据 | ⚠️ 调试时必须先等 10 秒 |
| **通信超时** | 控制循环 100Hz，**每秒**检查一次；收不到新指令即清零三轴目标速度 | ⚠️ 原以为 2 秒，实为 1 秒（20 Hz 仍有 20 倍余量） |
| 低压保护 | 固件 `voltage < 10` 切断 PWM | 10 V 是电池报废红线 |
| 物理使能开关 | `PD3`（主板左上角），ON 才允许电机使能 | 除 `Flag_Stop` 外的独立保护 |
| 堵转保护 | PWM 打满但编码器 <10 counts 持续 100 次 → `hall_stop` | 自带保护，无需我们实现 |

#### E.1 本次新发现的可用资源（二期加分项）

| 能力 | 引脚/依据 | 可能的用途 |
|---|---|---|
| **4 路 PWM 舵机** | `PC6~PC9` / `PB14` / `PB15`（TIM8/TIM12） | ⭐ **摄像头云台**——视觉跟随方案可直接用，不用外挂舵机驱动板 |
| **CAN 总线（1 Mbps）** | `CANH/CANL` 端子，ID `0x181` 控制 / `0x101-0x103` 回传 | 串口不够时的备选通道；比串口更抗干扰 |
| **12 个预留 IO** | PA11 / PB13 / PC13-15 / PD4,7,10 / PE7 | 扩展超声波、红外、TOF 等传感器 |
| **SWD 调试口** | `PA13/PA14` | 在线调试 / 重刷固件 |
| **板载 Type-C = ROS 口** | 丝印 `ROS` | 省掉 USB-TTL 模块，省一个宝贵 USB-A 口 |
| OLED 显示屏 | `PD11~PD14` | 可改固件显示自定义状态（如"正在听"、"NPU 负载"） |

> **对视觉方案的影响**：原计划若要做"摄像头追踪人体"的云台，需要额外买舵机驱动板 + 占 IO。
> 现在下位机自带 4 路 PWM 舵机接口，**云台可以直接挂上去，由下位机执行，
> Atlas 只需要通过串口下发"云台角度"指令**（需小改下位机固件，把预留位用起来）。

#### E.2 需要注意的下位机行为（务必写进调试手册）
