## 三、必须修正的问题（逐条详述）

### 3.1 ⚠️ 说明书自身有笔误 —— 我们之前"照抄说明书"反而是对的

**说明书第 19 页 表 2-7「底盘接收 ROS 发送过来的数据」写的是：**

```
帧头(固定值 0X7D) ... 帧尾(固定值 0X7B)
```

**这是印刷错误**——把帧头和帧尾写反了。同一页下面又说"首先要检测数据帧头"，而上一页表 2-4 明确 `tx[0]=0X7B` 帧头。

**固件源码 `usartx.c:907` 的真实逻辑：**

```c
if (Usart_Receive == FRAME_HEADER || Count > 0)   // FRAME_HEADER = 0X7B
    Count++;
else
    Count = 0;
```

**ROS2 官方驱动 `dlrobot_robot.cpp:56,82` 的真实实现：**

```cpp
Send_Data.tx[0]  = FRAME_HEADER;   // 0x7B
Send_Data.tx[10] = FRAME_TAIL;     // 0x7D
```

→ **我们的 `car_serial.py` 是对的（0x7B 头 / 0x7D 尾），不要被说明书表格带偏。**
建议在文档里显式记录这条"说明书笔误"，避免以后有人"以说明书为准"改错代码。

---

### 3.2 ❌ 严重错误：不是"2 秒超时"，而是 **100 ms**

我们所有文档都写了「下位机有 2 秒超时保护 / 20 Hz 保活即可」。**实际是 100 ms。**

**证据链：**

`BALANCE/balance.c` 平衡控制任务，**100 Hz** 运行：

```c
// This task runs at a frequency of 100Hz (10ms control once)
vTaskDelayUntil(&lastWakeTime, F2T(RATE_100_HZ));
if(i++ == 100)                 // ← 每 100 次循环 = 每 1 秒？不，是每 100 个 10ms 周期
{
    i = 0;
    if(RosCmdUpdate == 0)      // ← 这一秒内一个字节都没收到
    {
        Move_X = 0;            // ← 立刻清零目标速度
        Move_Y = 0;
        Move_Z = 0;
    }
    ...
    RosCmdUpdate = 0;          // ← 计数器清零，重新开始统计
}
```

而 `RosCmdUpdate++` 只在 `USART3_IRQHandler()` 里**成功校验一帧**时才执行（`usartx.c:929`）。

**精确定量**：`i++ == 100` 在 100Hz 循环里是每 **1.0 秒**触发一次（100 × 10 ms），
即**只要 1 秒内一帧合法数据都没收到，三轴目标速度立即被清零**。

> ⚠️ 更正说明：`RATE_100_HZ` 是 10 ms 周期，计数器到 100 → 1 秒。
> 但请**按 100 ms 设计**而不是 1 秒——因为一旦丢帧，
> 1 秒的空窗对运动中的小车是"溜车 1 秒"，非常危险。
> 我们的 `car_serial.py` 是 **20 Hz（50 ms）**，容错余量 = 20 帧，
> 实际上是**够用**的，但必须知道真实阈值，不能再写"2 秒"。

**结论与动作：**

| 项 | 原表述 | 修正为 |
|---|---|---|
| 超时阈值 | 2 秒 | **1 秒**（`RosCmdUpdate` 每秒清零一次） |
| 保活频率 | 20 Hz | **20 Hz 保留**，但说明"真实超时 1 秒，20 Hz 有 20 倍余量" |
| 影响 | 无需改代码，只需改文档口径 | — |

> **代码结论：`car_serial.py` 的 20 Hz 后台保活线程无需修改，设计是对的。**

### 3.3 ❌ 严重错误：Z 轴量纲不是 mm/s，转向系数错了约 6.5 倍

`car_serial.py` 的注释、GUI 文档、构筑方案都写「z 是 mm/s，角速度 ≈ 速度值 × 0.375 度/秒」。

**实际 Z 轴是角速度，单位 0.001 rad/s**：

- 说明书第 18 页原文：「Z 轴速度……最高位为0，正数(**逆时针旋转**)，速度大小为0(0.001rad/s)」
- 说明书第 16 页：「第7、8个字节：Z 轴速度……速度为 0(0.001rad/s)」
- 固件 `data_transition()` 里 Z 也是除以轮距+轴距得出，量纲是角速度

**正确换算：**

```
下发 short 值 N  →  角速度 = N × 0.001 rad/s
                 →  角速度 = N × 0.001 × 180/π ≈ N × 0.05730 度/秒
```

**所以我们原来写的 `DEG_PER_SEC_PER_UNIT = 0.375` 错了约 6.5 倍**
（0.375 vs 正确值 0.0573；若按 speed=200 算，旧值给 75 度/秒，正确值应是 11.46 度/秒）。

**注意：ROS2 官方驱动把 Z 也当成 m/s 处理了**（`Send_Data.tx[7..8] = angular.z*1000`），
说明厂商自己在上位机侧也没有按 rad/s 严格换算——所以**实机的转多快，最终只能靠卷尺/量角器标定**。
但从物理量上，Z 是角速度这一事实是明确的，不能再用"mm/s"描述。

**已修改：** `car_gui/car_gui_core.py` 增加了理论值常量并加注释：

```python
DEG_PER_SEC_PER_UNIT = 0.375   # ⚠️ 旧经验值（保留兼容），建议实机改为 0.0573
DEG_PER_SEC_PER_UNIT_RAD = 0.001 * 180.0 / 3.141592653589793  # ≈0.05730 理论值
```

### 3.4 ❌ USB 转串口芯片不是 CH343，是 **CH9102**

我们在文档里反复写「CH343 在 Linux 上枚举为 /dev/ttyUSB0」。

**厂商资料：**

- 主板资源分配表：「PA9.PA10 → USART1 → **TYPE-C-USB 串口1**」备注「**CH9102F** 串口」
- 「PD8.PD9 → USART3 → TYPE-C-USB 串口3」备注「**CH9102F** 串口」
- 说明书第 8 页：「底盘控制器板子上引出了串口1(**CP210**)和串口3(**CP210**)」（厂家自己也写混了）
- 原理图：两路都是同一颗 USB-TTL 芯片
- `软件和驱动/CH9102 USB驱动.EXE` ← **驱动包里给的就是 CH9102 驱动**

**影响：**

- **好消息**：CH9102 与 CH343/CH340 共用 `ch341` 内核驱动，在 Linux 下**同样枚举为 `/dev/ttyUSB0`**。
  所以**「`/dev/ttyUSB0` 而非 `/dev/ttyACM0`」这个结论依然成立**，代码不用改。
- **需要改的**：文档里的芯片名和 Windows 驱动名。上板子前如果先在 Windows 上用串口助手验证，
  **要装 `CH9102 USB驱动.EXE`，不是 CH343 驱动**。
- 更稳的做法：不依赖 USB-TTL 模块，直接用板子自带的 **Type-C 口（串口3 = ROS 口）** 连上位机，
  这样连 USB-TTL 模块都省了，也省一个 USB 口（对只有 2 个 USB-A 的 Atlas 是好消息）。

### 3.5 ❌ 遗漏：上电后 **10 秒**不能控制

**说明书第 22 页 + 第 19 页 + 固件 `USART3_IRQHandler` 三处一致：**

```c
if(Time_count < CONTROL_DELAY)      // #define CONTROL_DELAY 1000  (system.h:113)
    return 0;                        // 开机 10 秒前不处理数据
```

原文：「底盘控制器上电之后 **10s** 内电机是强制失能状态……在程序中设置了这 **10s** 内串口1 和串口3 不接收数据。」

**这条对我们的 GUI / 语音控制影响很大**：

- 用户上电 → 立刻启动 GUI → 点"前进" → **没反应，也没报错** → 会以为程序坏了。
- **建议**：GUI 连接成功后，若检测到 `flag_stop=1` 或回传速度恒为 0，
  在状态栏提示「下位机开机保护中（约剩 N 秒）」。

**`car_gui_core.py` 现有逻辑**：`_wait_feedback` 超时 2 秒会提示「下位机可能没在发数据」，
但**开机的 10 秒内下位机其实是在发数据的**（`data_task` 20Hz 一直在跑，只是不接收），
所以这个提示不会误报。**这块逻辑是安全的，但建议增强提示**。

## 四、需要补充的重要事实（加进文档，非错误）

### 4.1 电池/电压（12V 系统）

| 项 | 事实 |
|---|---|
| 电池规格 | **3S 或 4S 锂电**（`robot_select_init.h` 有 `BATTERY_3S` / `BATTERY_4S` 两档），电压为 **12V 级** |
| 保护阈值 | 固件 `Turn_Off()`：`if(voltage < 10 \|\| EN==0 \|\| Flag_Stop==1)` → PWM 全部置 0 |
| 厂商叮咛 | 「电池电压**不能低于 10V**。低于 10V 请停止使用……低于 10V 后再充电，容易造成电池损伤，无法正常充电」 |
| 板上电压表 | OLED 屏可显示（`Voltage_Show = Voltage*100`） |
| 满电参考 | 12V 系统满电约 12.6V（3S）/ 16.8V（4S） |

→ **我们的 `VOLT_LOCK = 10.0` 完全正确**，且它**同时是厂商规定的电池安全下限**（不只是告警线）。
→ **`VOLT_WARN = 10.8` 没有厂商依据**，是我们自己拍的。已改为 **11.0 V**（12V 系统留 ~1V 余量），并在代码里注明。
→ **建议加一条提醒**：「低于 10V 不仅停车，还会损伤电池，必须充电后再用。」

### 4.2 `Flag_Stop` 的正确语义

- 说明书：「flag_stop 是电机的停止标志位（**0 是使能、1 是失能**）」
- **注意**：这是**软件失能标志位**，不是硬件急停按钮。
- 另有**物理使能开关**（`PD3`，主板左上角）：开关在 ON 位置电机才使能。
- 固件里还有多个独立的保护源：`hall_stop`（堵转保护）、`hand_stop`、`NoControl_stop`（超时）、`stopkey_pressed`。
  其中 `hall_stop` 的判据是：PWM 打满 15960 但编码器 < 10 counts，持续 100 次 → 判定堵转。

→ 我们的代码统一叫 `flag_stop`，语义没问题。文档可补一句"此外还有物理使能开关 + 堵转保护"。

### 4.3 速度上限没有协议约束

`car_serial.py` 注释写「安全范围: -500 ~ 500」，文档写「协议安全范围是 ±500」。

**实际**：short 型 range 是 ±32767；固件不限制目标速度，只有 PWM 限幅 `Limit_Pwm(15960)`。

→ **±500 mm/s 是我们自己定的安全值**，不是协议限制。文档须改成"**项目自定安全范围**"，避免误解为协议硬约束。
→ 已修改 `car_gui_core.py` 里的错误注释。

### 4.4 `Check_Sum(22,1)` 与说明书"前22字节"一致 ✅

固件：`Send_Data.buffer[22] = Check_Sum(22, 1)` → 对 `buffer[0..21]` 异或。
说明书第 18 页：「第23 字节：BBC 校验位(**前22 字节异或**)」。
ROS2 驱动：`if (Receive_Data.rx[22] == Check_Sum(22, READ_DATA_CHECK))`。

→ **三方一致，我们的 `parse_feedback()` 用 `_xor_checksum(data[:22]) != data[22]` 完全正确 ✅**

### 4.5 上行 24 字节的权威字段表（三方交叉验证后）

| 下标 | 字段 | 类型 | 说明 |
|---|---|---|---|
| 0 | 帧头 | u8 | 0x7B |
| 1 | `Flag_Stop` | u8 | 0=使能, 1=失能 |
| 2-3 | X 轴速度 | short | mm/s（大端） |
| 4-5 | Y 轴速度 | short | mm/s，**仅麦轮/全向轮有效** |
| 6-7 | Z 轴角速度 | short | **0.001 rad/s** |
| 8-9 | 加速度计 X | short | raw，÷1671.84 = m/s² |
| 10-11 | 加速度计 Y | short | 同上 |
| 12-13 | 加速度计 Z | short | 同上 |
| 14-15 | 角速度计 X | short | raw，×0.00026644 = rad/s |
| 16-17 | 角速度计 Y | short | 同上 |
| 18-19 | 角速度计 Z | short | 同上（失能时置 0） |
| 20-21 | 电池电压 | short | **mV**，÷1000 = V |
| 22 | BCC 校验 | u8 | `buffer[0..21]` 异或 |
| 23 | 帧尾 | u8 | 0x7D |

**IMU 换算常数（来自 ROS2 官方驱动 `dlrobot_robot.h`）：**

```c
#define GYROSCOPE_RATIO   0.00026644f   // 量程 ±500°/s
#define ACCEl_RATIO       1671.84f      // 量程 ±2g = 19.6 m/s²
```

→ **这与我们 `car_serial.py` 的注释完全一致 ✅**（说明上一代已经核对过）

**IMU 坐标变换（固件 `data_transition()` 做了轴交换）：**

```c
Accelerometer.X_data =  accel[1];   // 加速度计 Y 轴 → ROS X 轴
Accelerometer.Y_data = -accel[0];   // 加速度计 X 轴 → ROS Y 轴
Accelerometer.Z_data =  accel[2];
```

→ **注意**：IMU 的物理坐标与小车运动坐标不同（说明书第 17 页：「X 轴正方向为向右，Y 轴正方向为向前，Z 轴正方向为上升」），
固件已做矫正。我们解析时**不需要再转换**。

> ⚠️ **发现固件的一个小 bug**（不影响我们，记录备查）：
> `send` 端 `data_transition()` 里，每次 `data_task` 都调用一次，`Check_Sum(22,1)` 在 24 字节协议下
> 是 `buffer[22]=校验`、`buffer[23]=0x7D`。但说明书第 21 页示例把电压按 **22584mV** 解释——
> 若真如此则 12V 系统读数会有问题。**建议实机读一次电压确认量纲。**

### 4.6 下位机可利用的额外能力（本次新发现，二期可用）

| 能力 | 依据 | 用途 |
|---|---|---|
| **板载 CAN（1 Mbps）** | `CANH/CANL` 端子，ID `0x181` 控制，`0x101/0x102/0x103` 回传 | 若串口不够，可换 CAN 通信 |
| **4 路 PWM 舵机** | `PC6/PC7/PC8/PC9/PB14/PB15`（TIM8/TIM12） | 摄像头云台！对视觉跟随很有用 |
| **板载 MPU6050** | `PB10/PB11/PB12` | 已在上行帧里，可直接拿姿态 |
| **OLED 显示屏** | `PD11~PD14` | 可显示自定义状态（需改固件） |
| **蓝牙（USART2）** | `PD5/PD6`，板上"跟蓝牙共用一个串口，二选一" | ⚠️ **与航模 IBUS 共用**，只能二选一 |
| **预留 IO 共 12 个** | PA11 / PB13 / PC13-15 / PD4,7,10 / PE7 | 扩展传感器（超声波、红外等） |
| **SWD 调试口** | `PA13/PA14` | 可在线调试 / 重刷固件 |

> **与 Atlas 的配合**：Atlas 只有 **2×USB-A + 1×USB-C**。
> 用板载 Type-C（串口3 = ROS 口）代替外置 USB-TTL 模块，**省下一个 USB 口**且更稳定。

### 4.7 7 种控制模式与优先级

说明书第 22 页列出 7 种模式及 OLED 显示：

| 模式 | OLED 显示 |
|---|---|
| CAN | `CAN` |
| 手机 APP（蓝牙） | `APP` |
| PS2 手柄 | `PS2` |
| 航模遥控 | `R-C` |
| **串口1** | `UART1` |
| **串口3（ROS）** | `UART3` |

**关键规则**（说明书第 19 页）：
「在 7 种控制机器人方式中，**ROS 的控制优先级是最高的**，在任意时候底盘控制器的串口3 接收到数据，则强制进入 ROS 模式。」

→ **这对我们极有利**：只要 Atlas 往串口3 发数据，就自动抢占控制权，
不需要先"解除"航模遥控/蓝牙模式。✅

> ⚠️ **副作用（须写进安全须知）**：如果航模遥控器还开着，
> 操作员**无法用手柄抢回控制权**——手柄指令会被 ROS 模式忽略。
> **调试时建议先关掉遥控器发射机**，避免"以为手柄能急停但实际不能"。

## 七、本次核对带来的三个"意外收获"

1. **板载 4 路 PWM 舵机接口**（`PC6~PC9/PB14/PB15`）——之前规划"摄像头云台"时以为要外挂舵机驱动板，
   实际下位机就带着，可以直接用来做**视觉跟随的云台**，二期视觉方案成本降低。

2. **ROS 控制优先级最高**——不用做"模式切换"，Atlas 一发数据就自动接管，
   对"语音控车 + 手动遥控无缝切换"的实现大大简化。

3. **板载 Type-C 就是 ROS 串口口**——省掉 USB-TTL 模块，也就省掉一个宝贵的 USB-A 口，
   对只有 2 个 USB-A 的 Atlas 200I DK A2 是实打实的利好（可以把 USB 口留给声卡和摄像头以外的外设）。
