# 多步指令规划器

> 一句话：「**先前进一米，再左转90度，再后退半米**」这类复合指令，现在会**按顺序分步执行**。
> 以前只会识别成其中**一个**动作。
>
> 前置阅读：《[语音识别（ASR）](语音识别-ASR.md)》《[本地与云端 LLM 接入](本地与云端LLM接入.md)》

---

## 一、它解决什么

```
你说：先前进5米，再左转90°
以前：只执行「前进」或「左转」其中一个  ← 用户反馈的痛点
现在：前进 → 停稳 → 左转 → 停稳，逐步执行，每步都能被急停打断
```

两条入口都支持：

| 入口 | 说明 |
|---|---|
| **规则快路径** `parse_plan()` | 按连接词（**再 / 然后 / 接着 / 之后 / 随后 / ; / ；**）拆片段，零延迟、零网络依赖 |
| **LLM 多步** `LlmReply.steps` | 规则没命中时，让云端 LLM 返回 `steps` 数组（仅 `mode=api` 云端模式） |

---

## 二、怎么用

**不用做任何事**，说人话就行：

```
「先前进一米，再左转90度」
「前进一米然后后退半米再左转30度」
「先前进半米，然后再左转45度」
```

**限额（写死在代码里，防"一句话把车开飞"）**

| 项 | 上限 | 超了怎么办 |
|---|---|---|
| 步数 | **3** 步 | 执行前 3 步、忽略后续（有日志）；被忽略段里若有停车词 → **整体退回单步** |
| 单步距离 | **1000 mm** | 截到 1 米，日志写明原值 |
| 单步角度 | **90°** | 截到 90°，日志写明原值 |

> ⚠️ **限幅只对"多步计划"生效**。单步指令（如"前进5米"）**保持原来的行为不截断** ——
> 这是刻意设计：单步是用户盯着车说的一句话，多步是"一句话指挥一串动作"，风险不同。

## 三、安全设计（**改代码前必读**）

### 3.1 每一幕仍走统一执行入口

```python
_run_plan(steps)
  for step in steps:
      self._do_action(step, ...)      # ← 唯一执行入口，安全闸门一份不少
      等待 duration + 0.25s（可被中止）
```

`_do_action()` 里的**急停锁定 / 连接判断 / 离线演示 / 播报**逻辑**全部复用**，
所以多步**没有绕过任何既有安全校验**。

### 3.2 急停能立刻中断（真机验证过）

```
第1步前进2s → 第2步左转0.8s → [发急停]
→ "⏹ 多步计划已中止：已执行 2/3 步"
→ 第3步从未下发，之后零新动作
```

机制：`trigger_emergency()` / `emergency_stop()` 里置 `_plan_abort` 事件，
计划线程每 0.1s 轮询该事件，**立刻停**。

### 3.3 中止后**绝不自动续跑**

必须重新下指令。这是刻意设计（`release_estop()` 只在**没有计划在跑时**才清中止信号，
防止"急停→没察觉→狂点解锁"把中止信号抹掉）。

### 3.4 运动期间不出声

本板**采集与播放双向硬件互斥**：运动时麦克风被 KWS 占着，**运动中途 aplay 会失败**
（`set_params:1416`）。所以：

- 开始前播一句摘要（「分N步开始」）→ **等它真播完**（`speak_idle()`）→ 才启动第 1 步
- 执行期间**不逐步播报**（`PLAN_SPEAK_STEPS=False`）
- 结束后播「N步都完成了」
- 超时兜底：抢占用播报（`yield_speaker()`），**保证运动中绝不出声**

> 真机实测（NPU TTS + 真 KWS 占麦）：摘要完整播完才动车，**无 `set_params:1416`、无 aplay 失败**。

## 五、⚠️ 已知限制（**上车前必读**）

### 5.0 本轮修掉的两个问题（独立验证挖出，记录留档）

#### B1（安全相关）多步计划曾经**冻结整个界面最长 60 秒**

**现象**：`_run_plan()` 会忙等整条计划跑完；而它原来是在**界面线程**里被同步调用的
（`_dispatch_text` 认为"规则命中"就同步执行）⇒ 计划期间**手动急停按钮和空格键点不动**。
实测最坏「前进5米×3」@speed50 = **60.75 秒**，tick 心跳间隔 4.7s。

**修法**：三条界面入口（文本发送 / PTT 识别后执行 / LLM 返回多步）统一走新的
`_exec_text()`：**多步计划 → 后台线程**（`_submit`），单步仍走原同步路径。
修后实测：`_dispatch_text` 返回 **0.005s**，心跳最大间隔 **0.091s**，计划照常跑完。

> ⚠️ 语音急停当时**仍然有效**（它在独立线程），但「点了没反应」本身是安全隐患，所以必修。

#### B1 的连带风险：计划并发（我加的补丁）

计划改到后台后，**计划执行中再说一句多步指令会并发两个计划**（原来被界面线程串行化了）。
两套运动帧互相覆盖，且 `_plan_abort.clear()` 会**抹掉正在跑的计划的中止信号 → 急停能失效**。

**修法**：`_run_plan()` 加**重入保护**（`_plan_lock` + `_plan_running` 占位）：
已在执行时**直接拒绝**（`"已有计划在执行"`，不排队、不覆盖）。要打断请先急停。
实测：第二条被拒，第一条仍正常跑完。

#### B2 限幅被四舍五入轻微突破

`round(dur, 2)` 会**进位**，反算回距离/角度会略微超限。扫描 speed=50..500 最坏：
**1002.25 mm**（上限 1000）、**90.87°**（上限 90）。
**修法**：改用 `_plan_dur_floor()` **向下取整**。修后最坏 **1000.0000 mm / 90.0000°**。

### 5.1 ✅ 速度/转向标定已完成（2026-10-17 真车实测）

**这条原本是头号未解问题，现在已经有实测答案了。** 两个根深蒂固的错误假设被推翻：

#### ① 速度命令值 **不是 mm/s** —— 差约 20 倍

一直假设"速度 50 = 50mm/s"，于是 `duration = 距离/速度`。**实测**：

| 命令值 | 实际稳态速度 | 说明 |
|---|---|---|
| ≤18.6 | **0** | 电机死区，不动 |
| 25 | 650 mm/s | |
| 30 | 1158 mm/s | 默认速度 |
| 50+ | 封顶 1500 mm/s（保守） | 高值未实测，防外推 |

拟合：**实际速度 ≈ 101.6 × (命令值 − 18.6) mm/s**，且**加速时间长达 3.1 秒**。

⇒ 旧代码 `1000/300 = 3.33s` 会让"前进一米"实际冲出**十几米**。
现已改为用实测模型换算（`cmd_to_mmps` / `duration_for_distance`），
并按 `20%` 量级修正了 `DEFAULT_SPEED 300 → 30`、`SPEED_MIN 50 → 25`、`SPEED_STEP 50 → 5`。

#### ② 转向死区高达 **138**（不是 18.6）

**实测现象**：计划"先前进半米，再左转30度"在真车上**只前进、没转**。
原因：默认命令值 30 远低于转向死区。

用命令值 100/200/300 各转 1.5 秒实测：

| 命令值 | 1.5 秒实测转角 | 推算角速度 |
|---|---|---|
| 100 | <20°（≈不转） | ~0 |
| 200 | 20~50° | ~23°/s |
| 300 | >90° | ~60°/s |

（方向正确：`turn_left` = 逆时针）

拟合：**角速度 ≈ 0.371 × (命令值 − 138) °/s**，转向**几乎没有加速延迟**。

⇒ 现在"多少度"这类指令**改用专用转向命令值 `TURN_CMD=250`**（≈41.6°/s），
不再沿用平移速度 —— 否则用户把速度调到 30 就永远转不了。

**实测验证**：「先前进半米，再左转30度」→ 前进 → 停 → 左转，**约 30°，符合预期** ✅

#### ⚠️ 仍有误差的地方（如实说）

- **低速顿挫**：命令值 25~30 只比平移死区高一点点，负载稍大就"顿一下"。
  实测同一命令值 3.0s 走 170cm、2.41s 却走 180cm（时间更短却更远）——
  **低速下距离精度只能到 ±50%**。这是物理限制。
- **转向精度 ±30%**：只测了 3 个点、每个 1.5 秒，转 90° 这种大角度误差会累积。
- **高命令值（>50）完全没实测**，线性外推不可信，已用 `SPEED_MMPS_MAX=1500` 保守封顶。

### 5.2 没有里程计：走多远靠时间推算（已用实测加速时间补偿）

协议只回速度、且 `vx` 恒为 0（**下位机不发速度反馈**，实测确认），所以只能按时间推算。
实测**电机加速时间 ≈ 3.1 秒**（比想象的久得多），所以短指令几乎不走。
已在换算里补偿 `加速时间/2`，但**低速顿挫**导致 ±50% 误差（见 §5.1 末）。

### 5.3 计划执行期间又来一条单步运动指令 → 会互相覆盖

例如多步跑到一半，第二次语音唤醒识别出"前进"。**计划不会因此中止**（只有急停/停车/断连/锁定会中止）。
未做 supersede 机制，属已知限制。

> ⚠️ 但**再来一条多步计划会被拒绝**（`"已有计划在执行"`，见 §5.0 的重入保护）——
> 那是为了避免两套计划互相覆盖 + 抹掉中止信号。

### 5.4 4 步以上 = 执行前 3 步 + 忽略后续

不是"整体拒绝"。若你更希望整体拒绝，改 `parse_plan` 里 1 处即可。

### 5.5 本地 LLM 模式不支持多步

本地 GBNF 语法文件未改（本次不改）⇒ `mode=server/cli` 下多步句**只执行第一个动作**，
这是**改动前既有行为**，不是回归。多步能力仅 `mode=api`（云端）。

### 5.6 云端偶发漏填 `confidence`

实测 1/6 多步句漏填 → 被置信度闸门（≥0.8）丢弃、整句退化为闲聊。
与单步行为一致（安全侧），未放宽。

## 八、排错

| 现象 | 原因 | 处理 |
|---|---|---|
| 多步只执行了第一个动作 | 该句走的是**本地 LLM** 模式（不支持 steps） | 用云端模式（`--llm-mode api` 或有 key 的 auto） |
| 转弯角度明显不对 | `DEG_PER_SEC_PER_UNIT` 未实机标定 | 按 §六 标定后改常量 |
| 第 3 步被忽略 | 超过 3 步上限 | 拆成两句说 |
| 前进距离偏短 | 电机起速 ~2s，无里程计 | 属固有误差，可标定补偿 |
| 计划中途不动了 | 可能已急停/锁定/串口断开 | 看日志「计划中止」原因；需重新下指令（不会自动续跑） |
| 运动时听到爆音/无声 | 正常：运动期间刻意不播报 | — |
