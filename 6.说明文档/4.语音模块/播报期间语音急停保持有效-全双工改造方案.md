# 播报期间语音急停保持有效 —— 音频全双工改造方案

> 适用：Atlas 200I DK A2（Ascend 310B4）+ 当前 `car_gui` 语音链路
> 日期：2026-10-19
> 目标：把「播报时麦克风打不开」的失聪窗口从 **整段播报 + 1~2 s** 压到 **0**，
> 并保证改造期间和改造之后都有一条不依赖语音的急停通道。

---

## 0. 结论（先看这 7 行）

1. **准确说不是「板载 codec 半双工」**——本板根本没有板载 codec。
   采集是 **PCM2902（纯 IN 端点）**，播放是 **SPACETOUCH（有 OUT 端点）**，
   两块 **USB 音频设备**（现有证据指向全速，用 `lsusb -t` 复核）
   挂在 **同一颗 xHCI** 上，抢同一份 USB 周期预算。
2. **换 USB 口没用**：两个 Type-A 都由 **RTS5411 hub** 分出，板子只有 **1 个 USB 主控**
   （`xhci-hcd/1p`）。这是本项目已经确认过的硬件事实。
3. **纯软件无法让「打不开的麦克风」打开**；但现有 1~2 s 恢复时间里，
   **约 0.85 s 是软件自己加的保守等待**（`0.25 s` 排空 + `0.6 s` 回声保护），可以先砍。
4. **推荐路线**：换 **单设备 USB 全双工声卡（High-Speed 优先，全速单设备也可先试）**
   （首选自带 AEC 的 USB 会议全向麦）
   → KWS 常驻不再让位 → 软件 AEC/门限防自触发 → **物理急停按钮兜底**。
5. **预期效果**：失聪窗口 **0**；急停从喊出到电机停 **≤ 0.5 s**；
   连续播报 100 句自触发 **0 次**。
6. **已排除**：I2S HAT（内核 `CONFIG_SND_DESIGNWARE_I2S` 没编）、蓝牙（`CONFIG_BT` 没编）、
   HDMI 音频（无 codec 驱动）、换 USB 口（单主控）、普通 USB hub（不增加上游带宽）。
7. **安全底线**：语音急停不能是唯一通道。物理按钮/无线急停必须与语音并行存在——
   这次改造要解决的是「单一通道在播报期失效」，而不是「把语音做得更响」。

---

## 1. 问题定性：到底是哪一层「互斥」

### 1.1 现场设备（已确认）

| 角色 | 设备 | USB ID | 端点 | 说明 |
|---|---|---|---|---|
| 采集 | `USB PnP Sound Device`（TI PCM2902） | `08bb:2902` | **只有 `0x82 EP 2 IN`** | `lsusb -v` 无任何 OUT 端点；`/dev/snd` 只有 `pcmC0D0c` |
| 播放 | `SPACETOUCH USB Audio` | — | 有 OUT | 无线麦接收器，采集端没有真麦（RMS 0.0004） |
| 串口 | CH9102 | — | CDC-ACM | 低速控制传输，不占等时带宽 |

两块音频设备都挂在 **RTS5411 hub → 单颗 xHCI** 下
（`lsusb -t` 看速率：`12M` = 全速，`480M` = 高速）。

### 1.2 三条现场证据

```text
① 麦克风被常驻占着 → 播放失败
   aplay: set_params:1416: Unable to install hw params

② 播放进行中 → 开麦失败
   PortAudio -9999: 'Input/output error' [ALSA error -5]

③ 内核日志里 USB 周期预算不够
   dmesg 见过 1660 次  Not enough bandwidth ... -28   ← -28 = ENOSPC
```

`-28 (ENOSPC)` 不是「设备被独占」的典型错误（那是 `-EBUSY/-16`），
它指向 **USB 等时（isochronous）周期预算分配失败**。

### 1.3 三个可能的机制（诊断脚本会区分）

| 机制 | 解释 | 对应现象 |
|---|---|---|
| **A. 全速周期预算** | USB 2.0 全速总线的等时预算按端点 `wMaxPacketSize` 预留，两块全速音频设备各占一条流，叠加超过 80% 周期上限 | 两设备都在时必失败；单设备正常 |
| **B. Hub 单 TT** | RTS5411 的 FS 事务翻译器（TT）周期缓冲有限，两条 FS 等时流同时过 TT 会顶满 | 换口无效；加 **MTT hub** 可能缓解 |
| **C. xHCI 调度/驱动** | 控制器对同时 IN+OUT 等时端点的调度限制 | 同卡全双工也失败 |

**不管哪一种，结论都指向同一件事：必须让「采集」和「播放」不要同时挤在一条全速 USB 音频通道上。**

### 1.4 现有软件的分时租借（以及它的代价）

```text
SpeakQueue._loop
   ├─ mic_pause()  → KwsListener.pause()  → 关 InputStream、让出麦克风
   ├─ tts.say()    → 逐句合成 + aplay（一句一个子进程）
   └─ mic_resume() → KwsListener.resume() → 循环重开 InputStream
```

关键代码位置：

| 行为 | 文件:行 | 说明 |
|---|---|---|
| 播报前暂停 KWS | `car_gui_core.py:2723` `_pause_kws_for_playback` | 注释明确写「对急停零损失」 |
| 播报后恢复 KWS | `car_gui_core.py:2752` `_resume_kws_after_playback` | **固定 `sleep(0.25)`** 等余音 |
| 回声保护窗 | `kws_engine.py:157` `ECHO_GUARD_SECONDS = 0.6` | 开流后 0.6 s 内忽略命中 |
| 录音让位 | `car_gui_core.py:2688` `_yield_mic` | 额外 `sleep(0.35)` |
| 播放调用点 | `tts_engine.py:1308` | 每个播报条目 pause 一次 |

**失聪窗口近似公式：**

```text
T_deaf ≈ T_播报（合成+播放）
       + 0.25 s（_resume 固定等待）
       + T_重开流（0.1~0.5 s，带重试）
       + 0.60 s（ECHO_GUARD）
```

一句 12 字播报，`T_deaf` 量级 **3~6 s**。
船长说的「播报结束后还要等一两秒」= 后三项，其中 **0.85 s 是软件策略，不是硬件限制**。

> ⚠️ 这也解释了为什么「播报时急停失效」和「播报一直失败」是同一枚硬币的两面：
> KWS 常驻 → aplay 失败；KWS 让位 → 急停失聪。分时复用只是把矛盾挪了个位置。

## 3. 第 0 步：先诊断，别先买东西

### 3.1 跑诊断脚本

> 💡 **如果你手上已经有「USB-A + 3.5mm 输入 + 3.5mm 输出」的声卡**，
> 先看 [现有设备全双工验证方案](现有设备全双工验证方案.md)——
> 那块声卡本身可能已经是单设备全双工，**不一定要买新设备**。

新增只读脚本 `car_gui/audio_duplex_probe.sh`，不改任何配置：

```bash
cd ~/car_gui
bash audio_duplex_probe.sh
# 指定设备：
CAP_DEV=plughw:0,0 PLAY_DEV=plughw:1,0 bash audio_duplex_probe.sh
```

它会输出：

1. `lsusb -t` 拓扑（看音频设备是 `12M` 还是 `480M`、挂在哪条 Bus）；
2. `arecord -l` / `aplay -l` / `/proc/asound/cards`；
3. 单独播放、单独采集（基线）；
4. **先播后录**、**先录后播** 两种顺序 × 多组采样率；
5. 同一张卡同时有 `pcmXp`/`pcmXc` 时的同卡全双工；
6. `dmesg` 里的 `-28` / bandwidth 记录。

### 3.2 结果怎么读（决策树）

```text
单独都成功、所有并发都失败
├─ 同卡全双工成功 ────────────→ 买单设备全双工声卡（S1/S2），最稳
│                              ⚠️ 若成功的是 SPACETOUCH，别高兴太早：
│                                 它的采集端没有真麦（RMS 0.0004），只能证明"控制器允许同卡并行"
├─ 某个低采样率组合成功 ──────→ 先把该组合做成默认，0 元解决（S0+）
├─ 加 MTT hub 后成功 ─────────→ Hub 单 TT 瓶颈；可临时用 MTT hub，但仍建议换单设备
└─ 全部失败且 dmesg 有 -28 ───→ 周期预算顶满；换**单设备**（HS 优先，S1）

同卡全双工也失败
└─ 控制器层限制 ─────────────→ 只能旁路 USB：网络音箱（S3）或 M.2 转 USB 控制器
```

> 诊断脚本会发 440 Hz 测试音。**先把音量旋钮调小**，并确认小车架起、不会突然动。

## 4. S1 / S2：硬件换通路（推荐主线）

### 4.1 改造思路

把「两条 USB 音频流抢一份周期预算」改成 **「一块设备内部同时跑 IN + OUT」**：

```text
改造前：  Mic(IN)  ─┐
                    ├─ RTS5411 hub ─ xHCI（一份周期预算，两条流各抢一份）
          SPK(OUT) ─┘

改造后：  ┌──────────── USB 单设备（HS 优先）────────┐
          │  ADC → IN 端点                          │
          │  DAC ← OUT 端点   （同一套 USB 配置）    │
          └───────────────┬─────────────────────────┘
                          └─ xHCI（同一设备统一分配，冲突面最小）
```

要点：**不是「再买一个 USB 声卡」，而是「把采集和播放合并到同一块设备」**。
两块独立设备是这次问题的根；换成一块设备后，两条流由同一套 USB 配置管理，
冲突面大幅缩小。**HS 是余量，不是硬门槛**——单设备全速也可先试，
但「两块设备」无论全速还是高速都不推荐。

### 4.2 两档配置

#### 配置 A（推荐）：USB 会议全向麦 / 会议扬声器

| 项 | 要求 |
|---|---|
| 设备类型 | USB 会议全向麦（speakerphone），**单设备同时有喇叭和麦克风** |
| 速率 | **480M 优先**；单设备 12M 也可先试（用 probe 验），关键是**不能是两块设备** |
| 协议 | UAC 1.0 或 2.0，Linux 免驱（`snd-usb-audio`） |
| 关键能力 | **内置硬件 AEC**（回声消除）、降噪、麦克风阵列 |
| 采样率 | 16 kHz 采集 / 22.05 或 16 kHz 播放均可 |
| 参考价 | 200~400 元 |

**为什么优先它：**
- 单设备 = 从根上消除「两块声卡抢总线」；
- 硬件 AEC 用设备自己的参考信号，延迟固定，比软件 AEC 稳；
- 麦克风阵列有指向性，播报声从喇叭到麦的耦合更低；
- 免驱 UAC，`aplay -l` / `arecord -l` 同卡出现，现有 `output_probe()` / `guess_input_device()` 基本能直接认。

#### 配置 B（预算）：USB 2.0 HS 声卡 + 现有领夹麦

| 项 | 要求 |
|---|---|
| 设备类型 | USB 2.0 外置声卡，**3.5 mm 麦克风输入 + 3.5 mm 音频输出** |
| 速率 | **480M 优先**；12M 单设备也可先试。市面大量「免驱声卡」是 12M，买前确认**单设备**、买可退 |
| 麦克风 | 现有领夹麦（3.5 mm） |
| 音箱 | 现有有源音箱（3.5 mm）；若现有音箱是 USB 专用，则选配置 A |
| AEC | 无硬件 AEC → 靠**声学隔离 + 软件 AEC**（见 5.3） |
| 参考价 | 40~80 元 |

**声学隔离比 AEC 更便宜有效**：领夹麦夹在衣领、离嘴 15~20 cm；喇叭朝下/朝外，
不要正对麦克风；播报音量用物理旋钮压到「能听清但不刺耳」。这样回声耦合先降 15~20 dB，
软件 AEC 的压力小很多。

### 4.3 买前验证（非常重要）

把商品页/客服问清这三条，缺一不买：

1. **是不是一块设备同时有录音和放音？**（硬指标；不是「一拖二」的两块芯片/两个 USB 设备）
2. **`lsusb -t` 的速率是多少？**（480M 更好；12M 单设备也可先试，**两块 12M 才是问题**）
3. **Linux/免驱 UAC 能不能用？**（不要买需要装 Windows 驱动的）

到货后先跑：

```bash
lsusb -t                       # 确认只有**一个**音频设备节点；480M 更好，12M 也可先试
arecord -l; aplay -l           # 同一 card 下同时出现 pcmXc 和 pcmXp
cat /proc/asound/cards
bash audio_duplex_probe.sh     # 并发矩阵应全绿
```

**验收不通过就退货**，不要先改代码。

### 4.4 备选：M.2 转 USB 控制器（不推荐优先）

板子有 M.2 Key M / Key E；Key E 已被 AX210 占用。若 Key M 空闲，可用
**M.2 Key M 转 USB 3.0 扩展卡**给系统加**第二颗 xHCI**，把播放设备挂到新控制器上。
成本 100~200 元，但：

- 需要确认 Key M 的 PCIe lane 可用、内核带 `xhci_pci`；
- 多一层转接，长期稳定性未知；
- 对「单设备全双工」没有帮助，只是把两块设备分到两条总线。

**只在 S1/S2 都验证失败时才考虑。**

## 5. 软件改造：让 KWS 常驻、播报不再让位

> 前提：S1/S2 的并发自检通过。否则不要打开 `CAR_AUDIO_DUPLEX=1`。

### 5.1 能力探测与开关

启动时做一次 **10 秒并发自检**（只在启动时做，不影响运行）：

```text
打开采集流 → 播 200 ms 测试音 → 采集流仍能读到数据？
  ├─ 是 → duplex=True，KWS 常驻
  └─ 否 → duplex=False，回退现有分时租借，并在界面显著提示
```

环境变量：

```bash
CAR_AUDIO_DUPLEX=auto   # auto（默认，自检决定）/ 1（强制并行）/ 0（强制分时）
```

**默认 `auto`**，失败自动回退——不允许因为换了个设备打不开麦，把语音急停整体搞挂。

### 5.2 KWS 常驻（核心改动，约 20 行）

| 位置 | 改动 |
|---|---|
| `car_gui_core.py:2723` `_pause_kws_for_playback` | `duplex` 时**直接 `return False`**，不暂停 |
| `car_gui_core.py:2752` `_resume_kws_after_playback` | `duplex` 时**直接 `return`**，不等待、不重开 |
| `tts_engine.py:1308` | 不改：`paused=False` 时本来就不会调 `mic_resume` |
| `kws_engine.py:736` `pause()` | 保留，供非 duplex 路径和录音让位使用 |

这样播报期间 `InputStream` 一直开着，KWS 一直在跑——**失聪窗口变为 0**。

### 5.3 回声消除（AEC）

播放时麦克风必然听到喇叭。两条路线，按设备选：

#### 路线 1：设备自带 AEC（配置 A）

会议全向麦内部完成 AEC，Linux 侧拿到的就是「已消回声」的采集流。
软件只需确认：

```bash
# 播报时录 3 s：回采电平应远低于不播时的电平
# 把 X 换成会议麦的卡号（arecord -l 查）；采集设备号不一定是 0
arecord -D plughw:X,0 -f S16_LE -r 16000 -c 1 -d 3 /tmp/aec_test.wav
```

若设备 AEC 默认关闭（部分型号要按按键/拨码），按说明书打开。

#### 路线 2：软件 AEC（配置 B）

信号链：

```text
TTS 合成 (22050, float32)
   ├─→ play_samples() → wav → aplay → 喇叭
   └─→ 参考环形缓冲（重采样 22050 → 16000）

麦克风 (44100 / 48000, int16)
   ├─→ 重采样 44100 → 16000
   ├─→ AEC：clean = mic − 自适应滤波器(参考, 延迟)
   └─→ sherpa KWS
```

实现要点：

| 项 | 做法 |
|---|---|
| 库 | `speexdsp`（`SpeexEchoState`，aarch64 可源码编译；比 WebRTC AEC3 好装） |
| 帧长 | 10 ms（16 kHz → 160 点） |
| 滤波器长度 | 覆盖 300 ms 延迟 → 4800 taps |
| 延迟标定 | 播 200 ms chirp，录回来做互相关，结果存 `~/.config/car_audio/aec.json` |
| 参考信号 | 在 `npu_tts_engine.play_samples()`（`npu_tts_engine.py:751`）里 tap 一份 |
| 失败降级 | `AEC_MODE=off` → 走 5.4 的「双门限 + 二次确认」 |

> ⚠️ 软件 AEC 的难点不是滤波，是**延迟对齐**。`aplay` 是独立子进程，
> ALSA buffer + USB 延迟每次可能差几十毫秒。必须做一次标定，
> 并在每次换设备/改 buffer 后重标。

### 5.4 防自触发（比 AEC 更关键的保险）

现有 `ECHO_GUARD_SECONDS=0.6` 是「播完 0.6 s 内一律不听」——在全双工下不能再用，
否则等于把失聪窗口搬到播报之后。改成**三重闸门**：

1. **文本白名单**：TTS 文本入队前过滤，**禁止包含任何 KWS 关键词**
   （`急停 / 紧急停止 / 小车急停 / 停车 / 刹车`）及其近义词。
   现有 `SPEAK_ESTOP = "已急停"`（`car_gui_core.py:291`）**正好是关键词**，
   建议改成 **「已停稳」** 或 **「已制动」**，从源头去掉自触发。
2. **标签感知抑制**：记录「刚刚播出的文本」，若命中标签出现在该文本里，
   在「播放期 + 0.6 s」内忽略**这个标签**；其他标签照常接受。
   这样播「已停稳」时用户喊「急停」仍然有效。
3. **双门限 + 二次确认**（无 AEC 时的兜底）：
   - 播放期间阈值上调 `+0.15`（0.25 → 0.40）；
   - 播放期间把 `COOLDOWN_SECONDS` 从 `1.0 s` 临时降到 `0.15 s`，
     否则第二次命中会被冷却吞掉；
   - 同一标签在 `1.2 s` 内连续命中 2 次才触发；
   - 真实喊话通常连续多帧；喇叭回声经过声学衰减，置信度更低。

> 三条闸门是**叠加**的，不是三选一。AEC 做得再好，也建议保留 1 和 2——
> 因为「已急停」这种播报内容一旦被自己听到，后果是**锁死**，不是误报那么简单。

### 5.5 急停路径保持不变

`_on_kws_hit`（`car_gui_core.py:2506`）的安全语义**一个字都不要改**：

```text
命中 → 记一笔 → trigger_emergency() 同步停车 + 加锁 → 投递播报（异步）
```

播报永远不能挡在停车前面。改造只影响「KWS 能不能听到」，不影响「听到之后做什么」。

### 5.6 界面与可观测性

| 状态 | 现在 | 改造后 |
|---|---|---|
| 播报中 | 「录音中暂停」（琥珀色） | **「播报中 · 仍在监听」**（绿色） |
| 回退模式 | — | 「播报中 · 语音急停暂停（硬件不支持并行）」红色提示 |
| 指标 | — | 每次播报记录 `deaf_ms`、`aec_erle_db`、`self_trigger_count` |

日志里加一行，方便验收：

```text
🎤 播报并行：deaf=0ms  aec=on(ERLE 23dB)  self_trigger=0
```

### 5.7 软件回退

任何异常（AEC 崩溃、设备掉线、开流失败）→ 自动回退 `duplex=False`，
回到现有分时租借，并在界面显著提示。**不允许静默降级。**

## 6. S4：物理急停兜底（必做，和 S1 并行）

语音急停再可靠，也不该是唯一通道。推荐两级：

### 6.1 一级：USB HID 按钮/脚踏（15~30 元）

- 一个免驱 USB 小键盘、脚踏开关或自定义 HID 按钮；
- HID 走**中断传输**，不占等时带宽，**播报期间照样有效**；
- 软件监听 `/dev/input/event*`，按下立刻 `trigger_emergency()`；
- 优点：不改硬件、不占 GPIO、插上即用。

```python
# 伪代码：evdev 监听，按下即急停
for event in dev.read_loop():
    if event.type == EV_KEY and event.value == 1:
        ctrl.trigger_emergency(reason="物理急停按钮")
```

### 6.2 二级：433 MHz 无线遥控 + 继电器（30~80 元）

- 接收模块接 40-pin GPIO 或直接串在电机使能回路；
- **串入使能回路前先确认下位机接线与常闭/常开逻辑**（断错线可能变成"按一下才通电"）；
- **不经过 Linux**，主控卡死/播报/重启都挡不住；
- 这是最高安全等级的做法，适合上车演示和答辩。

> 建议答辩时明确说：「语音急停是主通道，物理急停是独立安全回路」——
> 这比「我们的语音识别很准」更有说服力。

## 10. 为什么排除 I2S / 蓝牙 / HDMI（附证据）

| 路线 | 证据 | 结论 |
|---|---|---|
| I2S HAT（MAX98357A + INMP441） | `zcat /proc/config.gz \| grep SND`：`# CONFIG_SND_DESIGNWARE_I2S is not set`；`SND_SOC` 下无具体 codec 驱动 | 要重编内核；且本板内核源码与 openEuler 源树不一致，`insmod` 已实测 oops | 
| 蓝牙音箱 | `# CONFIG_BT is not set`，`/lib/modules/.../bluetooth` 目录不存在 | 整条 A2DP 路径不存在 |
| HDMI 音频 | 无 codec 驱动，HDMI 出不了声 | 不可用 |
| 换 USB 口 | 2×Type-A 均由 RTS5411 hub 分出，板子只有 1 个 xHCI | 换口无效 |
| 普通 USB hub | 不增加上游带宽，单 TT 反而可能更糟 | 除非是 **MTT** hub，且仅作诊断 |

> 如果未来真的要走 I2S：前提是拿到**板子真正那份内核源码**（不是 openEuler 源树），
> 打开 `CONFIG_SND_DESIGNWARE_I2S` / `CONFIG_SND_SIMPLE_CARD` + 对应 codec，
> 重编并烧录。风险远高于换一块 USB 声卡，不建议在一期做。

## 附录 D：2026-11-05 半双工提速实测（播报后 3~5 s → **约 0.1 s**）

> 背景：演示时不走网络播报（喇叭装在车上，声音必须从车上的 USB 声卡出来），
> 所以只能继续「半双工分时」。但实测「喇叭说完话 → 麦克风能再输入」要等 **3~5 秒**。

### D.1 延迟到底花在哪（真机日志证据）

`/tmp/car_web_restart.log` 里的真实片段：

```
[20:32:21] 🎤 播报结束，语音急停已恢复监听
[20:32:22] [KWS] KWS 麦克风暂时打不开（多半正在播报），0.3s 后自动重试…
[20:32:24] …0.5s… → [20:32:25] …1.0s… → [20:32:26] …1.7s… → [20:32:29] …2.0s…
```

⇒ 不是「麦克风真的不可用」，而是 **KWS 恢复时撞上"设备仍被占用"的瞬间状态，
掉进了 0.3 → 0.54 → 0.97 → 1.75 → 2.0 s 的指数退避**；
而每次失败的 `AlsaOpen` 本身还要几百毫秒（PortAudio 的 ALSA 后端很贵），叠起来正好 3~5 s。
另有 3 处固定等待也在拖后腿：`_resume_kws_after_playback` 里 `sleep(0.25)`、
`_open_stream` 里 `_BUSY_BACKOFF=0.5`、回声保护 `ECHO_GUARD_SECONDS=0.6`。

### D.2 改了什么（4 个文件）

| 文件 | 改动 |
|---|---|
| `kws_engine.py` | 新增**快速恢复窗口** `FAST_RESUME_SECONDS=2.0` / `FAST_RESUME_DELAY=0.02`：`resume()` 后 2 秒内用 20 ms 快轮询（先问 `alsa_capture_free()`，设备没空就不去做那次昂贵的打开），退避只在长时间打不开时才生效；`OPEN_RETRY_DELAY 0.3→0.05`、`OPEN_RETRY_MAX_DELAY 2.0→0.6`；`_BUSY_BACKOFF 0.5→0.05`；`ECHO_GUARD_SECONDS 0.6→0.15`（用户明确接受喇叭余音被再识别，可用环境变量 `KWS_ECHO_GUARD_SECONDS` 覆盖）；恢复成功时打印「播报后 XX ms 拿到麦克风」 |
| `car_gui_core.py` | `_resume_kws_after_playback`：固定 `sleep(0.25)` → 改为**确认声卡静音就立刻恢复**（去抖 2×20 ms，最多 0.3 s），并打印用时；`WAKE_RESTORE_DELAY 0.4→0.15` |
| `car_web.py` | 自动聆听等播报的判据 `speak_idle()` → **`playback_idle()`**（不等合成，省 ~1.1 s/句）；轮询 200→50 ms，失败退避 0.8→0.3 s |
| `car_gui_pyside.py` | 自动聆听同样改为 `playback_idle()`，不再等合成队列 |

### D.3 实测结果（Atlas 200I DK A2 真机）

| 指标 | 改前 | 改后 |
|---|---|---|
| **播报结束 → 麦克风恢复**（用户抱怨的那段） | **3~5 s** | **74~82 ms**（真实 `SpeakQueue` 链路 3 轮实测） |
| 判定静音 + 发起恢复 | 250 ms 固定 | **23 ms** |
| KWS 关麦让位（播报前） | — | 187 ms（受 0.2 s 读块限制，可接受） |
| 离线回归 | — | 13 通过 / 0 失败 / 1 跳过；急停单测 44 通过 |

改后 `car_web.py` 启动日志（真实运行）：

```
[21:29:18] 🎤 播报结束，语音急停已恢复监听（判断静音+恢复用时 23 ms）
[21:29:18] [KWS] KWS 恢复监听：播报后 75 ms 拿到麦克风
```

### D.4 代价与注意

- 回声保护从 0.6 s 降到 0.15 s：播报「已急停/停车」后，**喇叭余音有可能被 KWS 再识别一次**
  （这正是用户明确接受的部分）。若要更保险：`KWS_ECHO_GUARD_SECONDS=0.5 bash run_web.sh`。
- 若麦克风持续被别的进程占着（例如同时开了多个 `car_web.py` 实例），这里仍然是"等它释放"，
  不会变快 —— 先确认只有一个实例在跑。
