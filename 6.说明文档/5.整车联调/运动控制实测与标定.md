## 一、这次要解决什么问题

网页/语音能把指令发出去，界面也显示"前进/左转"，
**但小车在地上几乎不动；偶尔动了，走的距离和转的角度也严重不符。**

这不是"界面 bug"，而是**运动标定（速度单位、死区、角速度）整体错了**。
本文记录我们如何一步一步查出真相、如何重标、以及怎么验证。

> 一句话结论先说：
> **固件协议里的"速度命令值"就是 mm/s，我们却把它当成自定义单位又乘了 101.6 ——
> 于是所有速度慢 40 倍，"前进一米"实际只走 7 厘米。**

## 二、开始时的现象（三条，都真实发生）

| # | 现象 | 当时的第一反应（错的） |
|---|---|---|
| 1 | 落地后**车完全不动**，但日志显示"前进 命令值30（约 1158 mm/s）" | 以为电机没上电 / 电池没电 |
| 2 | 架空时轮子**确实在转**（回传速度非 0），但速度极慢 | 以为麦轮打滑 |
| 3 | 转向"几乎不转"，左转+右转后车头还残留十几度偏差 | 以为左右电机不对称 |

**关键教训**：日志里那句「约 1158 mm/s」是我们**自己算出来的**，不是实测值 ——
日志"看起来合理"掩盖了标定错误。**任何"换算量"都必须用独立基准验证一次。**

## 三、排查路线（按我们实际走的顺序，每步都留证据）

### 3.1 先确认"指令到底有没有发出去"

不能只看日志（日志是我们自己打印的），要看**固件回传帧**。
`/api/status` 里原本没暴露反馈字段，我们补了 `vx / vy / vz / flag_stop`：

```bash
curl -s http://127.0.0.1:8090/api/status | tr ',' '\n' | grep -E 'vx|vy|vz|flag_stop'
```

实测：

```
静止:            vx=0    vy=0  vz=0
命令 speed=150 → vx=149（几乎 1:1）
命令 speed=300 → vx=289~367
```

→ **结论 A：命令值和回传值基本 1:1，说明"命令值"没有经过奇怪的缩放。**
这已经强烈暗示：命令值本身就是物理单位。

### 3.2 读厂商协议源码（真相在这里）

```python
# car_serial.py
def set_speed(self, x=0, y=0, z=0):
    """设置目标速度 (mm/s)
    安全范围: -500 ~ 500
    """
```

上行帧注释也写明：`byte 2-3: X轴速度 (signed int16, mm/s)`。

→ **结论 B：协议里速度就是 mm/s，安全范围 ±500。**
我们代码里的 `V = 101.6 × (cmd − 18.6)` 属于**凭空多乘了 101.6**。

### 3.3 用遥控器做"人肉基准"（这一步最关键）

光看协议还不够 —— 万一固件实际行为与文档不符？
**小车自带的遥控器是唯一独立于我们代码的参照**：用它做"已知动作"，再积分回传数据。

做法（详见 §九 工具）：

```bash
# 板子上开录制（19~20 Hz 采 vx/vy/vz）
python3 record_feedback.py --duration 180 --out /tmp/rec.csv
# 用户用遥控器做：前进1米 → 左转90° → 后退0.5米 → 右转180°
python3 analyze_remote.py /tmp/rec.csv
```

实测结果（第一次遥控录制）：

| 动作 | `∫vx·dt` | `∫vz·dt` |
|---|---|---|
| 前进 "1 米" | **916 mm** | — |
| 后退 "0.5 米" | **−496 mm** | — |
| 左转 "90°" | — | 1515 |
| 右转 "180°" | — | 4026 |

→ **结论 C：`vx` 单位确实是 mm/s（916 ≈ 1000，偏差 8% 属目测误差）。**

### 3.4 用卷尺/量角器做绝对标定（最终判定）

让用户在走廊里用**卷尺量位移、量角器量角度**，直接给出"实际 vs 理论"。
这是唯一没有中间换算的测量，作为最终判据。

第一次实测（速度档「中」=300）：

| 项目 | 理论 | 实测 | 偏差 |
|---|---|---|---|
| 单条 前进 1 米 | 1000 mm | **100 cm** | 0% |
| 单条 后退 1 米 | 1000 mm | 90 cm | −10% |
| 原地转一圈 360° | 360° | 355~370° | −1.4~+2.8% |
| 演示路线 第 1/3 步 | 1000 mm | 85 cm | −15% |
| 演示路线 转角 | 90° | 95° | +5.6% |

## 四、发现一：速度单位错了 40 倍

### 4.1 错误模型

```python
SPEED_DEADBAND = 18.6          # 号称"电机死区"
SPEED_MMPS_PER_UNIT = 101.6    # 号称"稳态速度 = 101.6×(cmd−18.6) mm/s"
SPEED_RAMP_SEC = 3.1           # 号称"起步斜坡 3.1 秒"
```

参数名看起来严谨（还有死区、斜坡），**但它们是建立在一个错误前提上的拟合**。
实际行为：命令 30 → 车只走 **30 mm/s（3 厘米/秒）**，
比模型声称的 1158 mm/s 慢 **40 倍**。落地时肉眼就是"没动"。

### 4.2 正确模型（重写后）

```python
SPEED_DEADBAND = 0.0        # 实测无死区（命令30→回传30）
SPEED_MMPS_PER_UNIT = 1.0   # 恒等：1 单位 = 1 mm/s
SPEED_RAMP_SEC = 0.8        # 遥控器实测：0→稳态约 0.8 秒
SPEED_MMPS_MAX = 500.0      # 协议安全上限
SPEED_MIN, SPEED_MAX = 100, 500
DEFAULT_SPEED = 300         # = 0.3 m/s
```

界面档位也随之改：**慢/中/快 = 200 / 300 / 450 mm/s**
（依据：用户遥控"丝滑手感"实测均值 236~621 mm/s、峰值 734 mm/s，
300 落在区间内偏保守侧）。

## 五、发现二：转向命令值被"平移量程"卡死

### 5.1 现象

改完速度后前进正常了，**转向还是几乎不转**。

### 5.2 根因（两处叠加）

**① `_clamp_speed()` 同时管平移和转向**

```python
def _clamp_speed(v):
    return max(SPEED_MIN, min(SPEED_MAX, v))   # SPEED_MAX = 500
```

转向要发 `Z=1600` 才有明显转速，但被钳到 500 → 回传 `vz` 峰值只有 212~304，
而遥控器能到 **1505**（差 5~7 倍）。

**② 更隐蔽的一处：`parse_text_command` 在"判断动作之前"就钳位**

```python
# 旧代码顺序
speed = _clamp_speed(speed)      # ← 这里就把 1200 砍成 500
...
if "度" in t:
    speed = _clamp_turn(TURN_CMD)   # ← 后面再想改也晚了
```

所以"以 1200 的速度左转 1.5 秒"发出去的是 500，
**日志还显示 500，让人以为参数生效了**。

### 5.3 修法

```python
# 转向单独量程
TURN_MAX = 1600
TURN_MIN = 100

def _clamp_turn(v):        # 转向专用钳位
    return max(TURN_MIN, min(TURN_MAX, int(v)))
```

三处全部改用 `_clamp_turn`：
- `parse_text_command()`（按动作选量程，**在钳位处就判断是不是转向**）
- `move()`（下发前的最后一道）
- `parse_plan()`（多步计划里的转向步）

### 5.4 角速度标定（靠用户目测 + 迭代）

| 步骤 | 做的改动 | 命令 | 实测 | 结论 |
|---|---|---|---|---|
| 1 | `TURN_CMD` 250→1600 | 90°(2.00s) | 约 80° | ω≈40°/s |
| 2 | ω=40 → 90°=2.25s | 90°(2.25s) | **正好 90°** | ✅ |
| 3 | 复测 360°(9.02s) | 360° | 385° | 超转 6% |
| 4 | ω 40→42.7（90°=2.11s） | 360°(8.43s) | 370° | +2.8%，**收工** |

**为什么最后定 42.7 而不是 40**：360° 那次用回传积分独立验证过
（`∫vz·dt = 6375`，按遥控基准换算 ≈379°），与目测 385° 吻合，
说明确实超转 —— 取长行程为准（长行程里起步/刹车占比最小）。

最终：**Z=1600，42.7 °/s；90°=2.11 s、180°=4.22 s、360°=8.43 s**。

> 同时把 `duration_for_angle()` 的时长上限从 **8 s 放宽到 12 s**：
> 42.7°/s 转整圈要 8.43 s，卡在 8 s 会让"原地转一圈"永远走不满
> （旧上限导致单条 360° 只能转到 332°，当时只能拆成两段 180°）。

### 5.5 左右不对称？其实是对称的

一开始用户反馈"左转+右转后残留左偏 15°"，怀疑电机不对称。
用遥控器左右各转 180° 测得 `∫vz` = **3879 / 3897（差 0.5%）** →
**完全对称**。那次"残留偏差"其实是两侧转角都严重不足造成的错觉。
→ 不做单边补偿。

## 六、发现三：距离/角度的系统性偏差 + 补偿

标定对之后，剩下的偏差（卷尺实测）：

| 场景 | 偏差 | 原因判断 | 处理 |
|---|---|---|---|
| 单条前进 | 0% | — | 不动 |
| 单条后退 | **−10%** | 前后向机械效率不同 | `BACKWARD_GAIN = 1.10` |
| 多步计划里的前进步 | **−15%** | **连续冷启动摩擦**：计划是"前进→左转→前进"的连续短动作，每次都重新克服静摩擦，而斜坡补偿 `ramp/2=0.4 s` 偏小 | `PLAN_MOVE_GAIN = 1.15` |
| 单条 360° | −1.4% | 目测误差 | 不动 |
| 计划内转角 | +5.6% | 目测误差 | 不动 |

### 6.1 补偿必须和"模型距离"分开记（重要工程教训）

加了 `×1.15` 之后，自检脚本 `verify_presets.py` 立刻**假绿变假红**：
它用"模型距离 = v×(t−ramp/2)"算，补偿让 t 变长 → 算出来 2024 mm，
和期望 2000 mm 差太多。而真实距离其实是准的。

于是加了一个**唯一口径**函数：

```python
def distance_efficiency(action, in_plan=False):
    """模型距离 → 真实距离 的经验效率系数（<1 表示模型高估）"""
    e = 1.0
    if action == "backward": e /= BACKWARD_GAIN
    if in_plan:              e /= PLAN_MOVE_GAIN
    return e
```

自检脚本用它折算：`真实距离 = 模型距离 × distance_efficiency(...)`。
**以后再调补偿，只要改一处，自检自动跟着对。**

## 八、换一台车 / 重刷固件后怎么重做（可复制流程）

> 标定参数是**和车绑定的**，换底盘/换电机/刷固件都要重测。按下面顺序做，
> 大约 20 分钟。

### 步骤 1：确认回传字段能用

```bash
bash run_web.sh            # 启动服务
curl -s localhost:8090/api/status | tr ',' '\n' | grep -E 'vx|vy|vz'
```

### 步骤 2：验证速度单位（是否需要 ÷ 系数）

命令 150 和 300，看回传 `vx` 是否 1:1：

```bash
# 若回传≈命令 → 单位就是 mm/s，SPEED_MMPS_PER_UNIT=1.0、DEADBAND=0
# 若回传是命令的固定倍数 → 那个倍数就是 SPEED_MMPS_PER_UNIT
```

### 步骤 3：测起步斜坡

用 `record_feedback.py` 录一段"静止→前进"的过程，
看 `vx` 从 0 升到稳态用了多少秒 → 填 `SPEED_RAMP_SEC`（本次 0.8 s）。

### 步骤 4：测转向量程

从 `Z=500` 开始往上加（`以1200的速度左转1.5秒`），
看回传 `vz` 是否还随 Z 增长；同时让用户**目测有没有明显转起来**。
把"明显能转"的最小 Z 记为 `TURN_CMD`（本次 1600）。

### 步骤 5：定角速度（目测迭代 2~3 轮）

```bash
# 发一个已知角度，量角器量实际角度
以1600的速度左转2秒      # 期望 2s×ω
# 用 实际角度/时长 得到 ω → 反填 TURN_DEGPS_PER_UNIT
# 再用 360° 复测一次（长行程更能放大比例误差）
```

### 步骤 6：卷尺测距离，补方向/场景系数

分别测"单条前进1米 / 单条后退1米 / 计划内前进1米"，
偏差 >5% 就填 `BACKWARD_GAIN` / `PLAN_MOVE_GAIN`。

### 步骤 7：回归 + 落实验收

```bash
python3 verify_presets.py     # 算术层
bash bench_web.sh             # 行为 + 安全层（小车必须架空！）
# 最后落地，按《装车验收清单.md》走
```

## 十、踩过的坑（按重要性排序）

1. **命令值 ≠ 物理量**：日志里"约 1158 mm/s"是自己算的，不是实测。
   任何换算量都要用**独立基准**（遥控器/卷尺/量角器）验证一次。
2. **钳位要按通道分**：转向和直行的量程不同（1600 vs 500），
   而且**钳位必须发生在"判断动作之后"** —— 否则后面的判断再正确也没用。
3. **`vz` 反馈不能跨控制路径比较**：遥控转 180° 时 `vz`≈1400~2200，
   App 发 `Z=1600` 时只有 790~836，但肉眼看转速接近。
   说明 `vz` 是"轮速当量"，两条路径换算不同 → **转向只能同路径标定**。
4. **回传积分会漏掉起步/刹车段**：只在 `|vz|>阈值` 的样本上积分，
   短行程必然偏低 → **反推必须用长行程**。
5. **补偿系数必须同步到自检**：否则模型距离会"假绿"（见 §6.1）。
6. **CSV 必须逐条 flush**：否则数据积在缓冲区，进程一被杀就全丢（样本=0）。
7. **停止文件按 mtime 判断**：`/tmp/xxx_stop` 若是 root 建的，
   HwHiAiUser 删不掉 → 旧实现"一启动就退出"、样本 0。
8. **单条命令时长上限要够**：8 s 上限会让"原地转一圈"永远差一截（本次放宽到 12 s）。
9. **目测精度只有 ±10°**：别用短行程反推角速度，也别为 3% 反复改参数，
   会陷入"改一下、测一下、又改回来"的循环。
10. **验证看门狗要"发动作后不再心跳"**：只发 `/api/action` 不续心跳，
    3 秒内必须自动停，这才是真实断网场景。
